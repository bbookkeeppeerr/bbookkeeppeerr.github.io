Improving my vscode setup

I'm not going to lie, it's been a while since I had to do raw html (my normal day job involves using frameworks, react for the most part). Part of doing this less polished method of webpage creation is to experiment with going back to basics a bit more (and allow me to experiment a little bit, instead of forcing me into the look that a normal static site generator would do)

So yes, I'm writing this using vscode. In order to add some extra valiation (including things that I didn't think about when making other pages twenty years ago now) I'm experimenting with the following vscode plugins

html-validate

Pre setup

Because this requires node, and my version on this laptop was very old I needed to update. The following got me up to node v24 (I did already have node and nvm installed) 

        
nvm install --lts
nvm alias default 'lts/*'
nvm use default

install

Run npx html-validate --init to install and setup the default .htmlvalidate.json file

I only chose the default and markdown rules (in case I decide in the future to go back to generating webpages through markdown). Afterwards I ran npx html-validate . to confirm it would run against the local files and detect failures (it does, I've been very sloppy).

In order to get it installed in vscode, I ran 'ext install html-validate.vscode-html-validate' (cmd+p) https://html-validate.org/usage/vscode.html had the instructions

Now this left me with a problem, I already have prettier installed, and some of the rules do conflict with what prettier thinks is correct (lowercase vs uppercase DOCTYPE for example).

Disabling prettier for html files is the quickest way to deal with that type of thing so I added a new .prettierignore file with *.html, but now formatting the file on save wasn't doing anything (so I could end up with non-matching indentation for opening and closing brackets for html files) - what to do...

I next tried adjusting the vscode settings.json file, thinking maybe switching the html formatter back to vscode default instead of prettier was the right move. so changing: 

        
"[html]": {
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
}

to

        
"[html]": {
  "editor.defaultFormatter": "vscode.html-language-features",
  "editor.formatOnSave": true,
}

but this didn't work when trying it out, so set it back to prettier-vscode

after more googling, discovered that I could add a set of rules to the .htmlvalidate file to avoid this issue 

        
{
  "extends": [
    "html-validate:recommended",
    "html-validate:prettier"
  ]
}

this also allowed me to get rid of the .prettierignore file completely, and keep both the formatting on code save and these new correctness checks

Axe Accessibility Linter

Accessibility is one of those things that I wish I knew more about when making things. It tends to be one of those things that people assume the UI framework will take care of for them already, and so doesn't get as much attention as the endless list of new features that people want to cram in. So I decided to see what this would catch for me.

Install

Download and install deque-systems.vscode-axe-linter in visual studio. Either from the link or through ext install

Checked the output logs in visual studio to make sure the install had worked, then added an empty <input> in order to trigger it so I could confirm it was picking things up correctly

Stylelint

CSS is also something which I tend not to stray too far away from whatever framework defaults are, or for more official pages whatever the design layout of whatever my employer uses. Since at least part of the impetus for doing this was to get back to trying to make something more unique that felt like myself (looks, layout and design wise) I decided that this would help make sure that the .css was keeping to some type of consistency

Install

Download and install stylelint.vscode-stylelint either from the link directly or through ext install

I could see from the vs code output that this wasn't working out of the box, and reading the linked webpage showed there was some extra setup needed. In summary:

create the stylelint.config.mjs file with the following contents: 

        
/** @type {import('stylelint').Config} */
export default {
  extends: ["stylelint-config-standard"]
};

run npm add -D stylelint stylelint-config-standard

ran npx stylelint "**/*.css" on my folder to see what it would detect (thankfully my css already had some errors it could pick up )

There are ways to change the settings in vscode to add extra file types stylecheck would run against, but I decided to keep with the defaults. After restarting vscode it picked up the new .mjs file correctly and started seeing the error lines in vscode
